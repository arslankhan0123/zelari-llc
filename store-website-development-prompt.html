Implementation brief · English prompt

Build a Complete Storefront Connected to My Ecommerce Admin Panel

Copy the prompt below into your coding assistant. It explains that the public website and the Laravel backend must work together, so products entered in the existing admin panel appear on the storefront and customer orders return to that same admin system.

Project context: This Laravel project already has admin management for parent and subcategories, products, customers, and orders. The goal is to build the customer-facing website and complete its functional connection to the existing backend while preserving those admin modules.

Prompt

Act as a senior Laravel full-stack developer and ecommerce UI/UX designer. Inspect my existing project before changing code. Build a complete, production-minded online store with a polished customer-facing frontend connected to a functional Laravel backend and my existing admin panel.

Do not create a disconnected visual mockup, hardcode sample products, replace working admin features, or duplicate existing database modules. Reuse the current Laravel architecture, Blade views, routes, authentication, database, models, and admin CRUD screens wherever possible. Explain and implement the real data flow from the admin panel to the storefront and from customer checkout back to admin order management.

1. Start by understanding the existing project

  1. Inspect project instructions, framework and frontend setup, routes, controllers, models, migrations, Blade layouts, middleware, and current admin screens.
  2. Confirm how parent categories and subcategories are represented, how product images and prices are stored, and which order statuses and payment methods the existing admin supports.
  3. Identify existing storefront or cart code and build on it. Where a requested feature is missing, implement it using the project conventions.
  4. Keep existing admin URLs, permissions, and workflows working. Do not remove or weaken admin authentication.

2. Create the customer-facing website

Design a distinctive, premium, current-looking ecommerce experience. Use a consistent brand style, excellent typography, strong product photography, considered whitespace, responsive layouts, clear calls to action, and refined colors and surfaces. Add smooth, lightweight page transitions and micro-interactions for menus, product cards, add-to-cart feedback, and loading states. Respect reduced-motion accessibility preferences. Make every page usable on mobile, tablet, and desktop.

  • Home: responsive navigation, prominent hero and shop action, category highlights, featured or newest products, promotions, store benefits, and footer with contact and useful links.
  • Shop: searchable and sortable product listing, category navigation, responsive left-side filters on desktop, a convenient filter drawer on mobile, pagination, product count, and helpful empty states.
  • About: editable, polished brand story and trust-building content.
  • Contact: contact details and a validated form with clear success and error feedback.
  • Product details: product gallery, name, price, sale price when present, description, category, stock availability, quantity selector, and add-to-cart control.
  • Cart: cart items with images and prices, editable quantities, remove controls, subtotal, any configured shipping or discount, and a checkout action.
  • Checkout: customer and delivery information, order summary, transparent total, and payment options supported by the application.
  • Order confirmation: order number, item list, quantities, charged prices, totals, delivery details, payment method, and next steps.

3. Connect the storefront to real admin-managed products

The product catalog shown to shoppers must come from the existing database and admin-managed records. When an administrator creates or updates a product, changes its name, price, description, category, images, or stock, the storefront should use that saved data automatically. Do not require a developer to edit a Blade file to publish a new product.

  • Show products only when their existing product status makes them available for sale. Hide drafts, inactive products, and inactive categories from public shopping.
  • Use actual product names, slugs, SKU where useful, feature images, additional product images, descriptions, category relationships, sale prices, and available quantity.
  • Support product detail pages linked to stable, readable product URLs and return a proper not-found response for unavailable items.
  • Build category menus dynamically from the database. Show parent categories and their subcategories without hardcoding the category list.
  • When a shopper selects a parent category, show products belonging to it and, where appropriate, its descendants. When they select a subcategory, show the products belonging to that selection.
  • Provide useful search and filters for category/subcategory and price range. Add sorting for price and newest, plus relevance when implemented meaningfully. Preserve filter and search selections while paginating.
  • Use database queries with sensible eager loading and pagination. Avoid loading the entire catalog into memory or issuing a query for every product card.

4. Implement the complete shopping and order journey

  1. Browse: The shopper opens the home page, follows a dynamic category or subcategory link, searches or filters the catalog, and opens a product.
  2. Add to cart: The shopper chooses a quantity that is available and adds the product. Show a clear confirmation and update the cart count. The cart must persist across navigation and refreshes using an appropriate session or existing account approach.
  3. Review cart: The shopper changes quantities or removes items. Recalculate totals and validate availability whenever cart contents change. Explain when an item is unavailable or stock is insufficient.
  4. Checkout: Collect and validate customer name, email, phone, shipping address, and city or the fields already used by the project. Let the shopper review products, quantities, shipping, discounts if applicable, and final total before submission.
  5. Choose payment: Use the payment methods already represented in the project. Support Cash on Delivery where configured. Do not claim card payment is operational unless a real payment provider is configured, credentials are present, and payment confirmation is verified server-side.
  6. Place order safely: Validate submitted product identifiers and quantities on the server. Reload current product prices and stock from the database; never trust a price, discount, shipping amount, or grand total sent by the browser. Recompute the order total on the server.
  7. Save atomically: In a database transaction, create or correctly associate the customer, create the order, and save a snapshot of each purchased line in order items, including product name, SKU when available, unit price, quantity, and line subtotal. Keep order records accurate even if product data is later changed or deleted.
  8. Protect inventory and checkout: Prevent quantities greater than stock. Update stock only as part of a successfully committed order, using safe locking or equivalent protection against two shoppers buying the last item at once. Roll back the order and stock update together if saving fails.
  9. Handle retries: Prevent accidental duplicate orders from a repeated submit or refresh. Show understandable validation errors and do not discard the cart after a failed checkout.
  10. Confirm: After successful order placement, clear or finalize the cart and show a confirmation page tied to the newly created order. Do not expose another customer's order through guessable public identifiers.

5. Make every order visible in the existing admin panel

A successful storefront checkout must create an order that appears in the existing admin Orders list and opens in the existing order detail page. Reuse the existing order and order-item relationships instead of creating a separate storefront-only order store.

The administrator must be able to see the order number, customer association and contact details, shipping details, purchased product snapshots, quantities, unit prices, line subtotals, order subtotal, shipping fee, discount if applicable, final total, payment method, payment status, order status, notes, and creation date. Preserve the admin's existing ability to search, inspect, and update order and payment status. Keep customer records correctly linked so the order appears in that customer's history.

6. Backend and security requirements

  • Use Laravel controllers, named routes, models, form validation, CSRF protection, and Blade components consistently with this project.
  • Keep admin-only operations behind the existing authentication and authorization middleware. Never trust the browser to authorize an order or modify admin data.
  • Validate and normalize incoming data; safely handle duplicate customer emails according to existing database rules.
  • Use transactions for order creation and stock changes. Avoid negative stock, invalid quantities, stale prices, and partial orders.
  • Escape user content in views and add accessible labels, keyboard-accessible controls, visible focus states, and useful error messages.
  • Use configuration and environment variables for external services. Do not commit secret credentials or invent successful payment behavior.
  • Add database migrations only when a genuine missing requirement cannot be represented by the existing schema. Explain why each added field or table is needed.

7. Make the site easy to operate

The existing admin panel remains the source of truth for products, categories, stock, customers, and orders. An administrator should be able to add a parent category or subcategory, add a product and its images and price, mark it active, and have it appear in the correct storefront category without manual code edits. When its stock reaches zero or the product is made inactive, the customer experience should reflect that state and prevent purchase.

8. Delivery requirements

  1. Implement the actual working frontend and backend integration, not only a design concept or implementation plan.
  2. Summarize the routes, controllers, views, database changes, and important files added or updated.
  3. Describe the full data path: admin product creation → public catalog → cart → validated checkout → database order and stock update → admin order list and detail page.
  4. List any environment setup required and clearly identify integrations, such as online card payments, that need real credentials before they can work.
  5. Report which checks you ran and their results. Do not claim a feature is functional unless it was implemented and verified.

Success means: an administrator can add and activate a product in the existing panel, a shopper can find it on the responsive storefront, add it to a persistent cart, complete a safely validated checkout, receive a clear order confirmation, and the administrator can see and manage the exact order in the existing admin panel.
